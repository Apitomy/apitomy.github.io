    Workbench Phase 2b: AI Turn Loop and Agent Tools Implementation Plan

    For agentic workers: REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (- [ ]) syntax for tracking.

    Goal: Let an AI agent work on a composition in turns. It reads and edits drafts through a dedicated MCP server, proposes workflow changes as Flow change sets, inspects real stream events, and evaluates EL expressions. The UI receives each finished turn as one combined change set and can undo a turn.

    Architecture: - Session binding: a composition is bound to one interactive assistant session created from the new built-in template axiom-workbench (capability composition). That session runs the new axiom-workbench MCP server. - MCP-only routes: the server calls REST routes under /compositions/{id}/agent/.... One shared SessionTokenGuard checks the session token on all of them. - Turns: CompositionTurns keeps the in-memory state of a running turn: the base workflow, the workflow with the turn's changes so far, and the ops. When the turn completes, it stores a pending change set and announces it over SSE. The editor applies it, which is Phase 4. - Restarts: WorkbenchSessions restores the chat history from history.jsonl and starts a new agent process. The next turn begins with a recap. - Expressions: ExpressionService evaluates EL with Flow's ConditionEvaluator, using the same scope the engine provides at each point.

    Tech Stack: Java 25, Quarkus 3.40.1, Panache, Jackson, Apitomy Flow engine 3.0.1 (io.apitomy.flow.changeset.*, io.apitomy.flow.engine.ConditionEvaluator), Node.js MCP server (@modelcontextprotocol/sdk), JUnit 5, RestAssured, Mockito (@InjectMock), node --test.

    Spec: docs/superpowers/specs/2026-10-08-workflow-workbench-design.md, especially §1 "MCP server", "Template", "The turn loop", §2 "Right pane" (Undo AI turn), §3 and §4. Phase 2a is merged on feat/workflow-first; its composition classes live in app/src/main/java/io/apitomy/axiom/app/composition/.

    package io.apitomy.axiom.app.assistant;

import jakarta.enterprise.context.ApplicationScoped;
import jakarta.ws.rs.WebApplicationException;

/**
 * The single check used by every REST route that only a session's own MCP server may call. The token keeps
 * sessions apart and stops casual local callers. It does not protect Axiom from the agent itself, which can
 * read its own token from its environment.
 */
@ApplicationScoped
public class SessionTokenGuard {

    /** Request header carrying the session's MCP token. */
    public static final String HEADER = "X-Axiom-Session-Token";

    /**
     * Requires the presented token to match the session's token.
     *
     * @param session the live session the route belongs to, or null if none is running
     * @param presented the header value, possibly null
     * @throws WebApplicationException with status 401 if the session is missing or the token does not match
     */
    public void require(AssistantSession session, String presented) {
        if (session == null || !session.verifyMcpToken(presented)) {
            throw new WebApplicationException("Missing or invalid " + HEADER, 401);
        }
    }
}
