    Workflows

    Workflows let you define a multi-step automation — including branching, human approvals, timed waits, and event-triggered branches — as a versioned, visually authored graph of nodes. Every workflow run operates on a single subject (an issue, a pull request, a Jira ticket, or a named subject created by a schedule trigger) and drives that run's tasks.

    If you haven't read Concepts yet, it introduces subjects, runs, events, and schedule triggers.

    Node Types

    Node Type Purpose
    start Workflow entry point; declares the inputs the workflow expects (see Workflow Input Contract)
    end Workflow termination
    action Creates a task for an action type and waits for it to complete before advancing. This is the only way an action type is ever executed; every action type appears in the editor palette.
    human-task Pauses execution until a user completes a form through the Inbox (see Human-Task Nodes)
    wait Pauses the instance for a fixed duration, then resumes automatically
    receive-event Pauses the instance until a matching stream event is dispatched to it

    The main configuration of each node type:

    Node Type Configuration
    start inputs: the run's declared inputs, each with name, type, required and description; only the standard inputs subject and event may be declared, and both have type object
    end None. Ends the run, or the current branch of a parallel region
    action actionType (an action type name, or sdk:<function>); inputs: a map of input name to EL expression; optional outputs to rename or require task outputs. Task outputs are merged into the run context under their names
    human-task Optional title and description; inputs shown to the person; outputs: the form fields, whose answers are merged into the context
    wait duration: an ISO-8601 duration such as PT1H or P1D
    receive-event eventType (required); optional match conditions, outputs ({contextKey, expression}), correlationKey, lookback and timeout (see Dispatching Events to a Waiting Workflow)

    Edges

    Edges connect nodes. Each edge may carry a priority, an EL condition, a default flag, and a label. Conditions let a node branch to different next steps based on the values already in the run's context (e.g. an action's output, or a human-task's submitted answers). The rules are:

    • A node with a single outgoing edge uses an unconditional edge that is not marked default.
    • A node with conditional edges (an exclusive choice) needs exactly one default edge, without a condition. It is the fallback when no condition matches. This includes a node with a single conditional edge.
    • Mark an edge as default only for such conditional choices. A node has at most one default edge.
    • Several unconditional, non-default edges leaving one node form a fork: the branches run in parallel. Do not mix fork edges with conditional or default edges. Parallel branches must re-join at a single node before they reach an end node.
    • Edges leaving the same node should have distinct priorities.
    • A receive-event node with a timeout needs exactly one timeout edge plus a normal outgoing edge.

    Expressions

    Conditions, action input mappings, human-task titles and receive-event settings are Jakarta Expression Language (EL) expressions, written without ${}. They read context.<key> (the run context: inputs and merged node outputs) and, where an event is involved, event.<field>. Action inputs can only read context; use context.event for the triggering event. Examples:

    • context.needsInfo == true
    • context.priority eq 'high' and not empty context.assignee
    • 'Review ' += context.subject.ref (join text with +=)

    EL has no fallback operator. a || b is a boolean OR and ?? is not valid syntax. To fall back to a default value, use empty: empty context.label ? 'triage' : context.label.

    Authoring a Workflow

    Navigate to Components > Workflows and click Create Workflow Definition. New definitions are scaffolded with a Start node (declaring the standard inputs subject and event, both required) connected directly to an End node — extend the graph from there.

    The Design tab holds the workflow editor (Apitomy Flow 3.0.2). It lets you add and connect nodes, configure each node's inputs and outputs, and edit conditional edges. An action node must map every required input of its action type, usually from the run context (context.subject.id, context.subject.name, context.subject.ref, context.subject.repository, context.event) or from outputs of earlier nodes; optional inputs may be left unmapped. See Inputs, Placeholders and Mappings. Click Save to store your changes as draft content on the definition; they are not usable by running instances until you publish.

    To build a workflow together with its action types and tools, with an AI assistant at hand, click Open in workbench (available once your changes are saved). See Workflow Workbench.

    Publishing and Versions

    Click Publish on the workflow detail page to validate the saved draft and create a new immutable version. Publish is disabled while there are unsaved changes or validation errors. Publishing fails with a description of the problem if:

    • The graph is structurally invalid (e.g. disconnected nodes, missing Start/End, or edges that break the rules in Edges)
    • The graph contains a node type Axiom doesn't support
    • The Start node declares an input other than the standard inputs subject and event, declares one with a different type, or gives one a default value (see the Workflow Input Contract)

    Each publish creates a new version. The Versions tab lists every published version, lets you diff any two versions side by side, and shows which version is currently active (currentVersion). Existing runs continue to use the version they were started with — publishing a new version never changes the definition an in-flight run is executing. The Runs tab lists the runs of the definition.

    Triggering a Workflow

    A workflow run can be started in these ways:

    • Manually from a stream event — on an event's detail page (Events > Event Stream, then click an event), click Run workflow… and pick any published workflow. Workflows used by subscriptions that matched the event are listed first, under Suggested. You may supply a title and labels. The run is started as a create-workflow rule would start it: on the subject found or created from the event's ref, with the event in its context as event. Manual runs get the label trigger:manual. REST: POST /api/v1/stream/events/{eventId}/runs.
    • From a subscription — a subscription routing rule of type create-workflow finds or creates a subject from the triggering event's ref, then starts the specified definition with its declared subject and event (the triggering event's envelope) inputs in its context.
    • From a schedule trigger — see Schedule Triggers below.
    • By re-running a failed run — see Re-running a Failed Run below.

    Run Title, Labels, and Inputs

    A run can have a title of at most 500 characters. A run gets one when it is started with one (for example from the Title field of an event's Run workflow… dialog, or the REST API), or when the workflow sets it with the axiom_set_workflow_run_title SDK function (see Axiom SDK Functions); lists and headers name other runs by their subject and workflow. Runs also carry free-form key/value labels (runs started by a schedule trigger are labeled trigger: schedule). A run cannot be started with supplied inputs: its inputs are always resolved by Axiom (see below).

    A run's context starts with exactly the standard inputs its Start node declares: subject (always available) and event (available only when the run was started from a stream event). A declared optional input that is not available is absent; a declared required input that is not available stops the run from being created with Cannot start workflow "<name>": required input(s) not available: <names>. New workflows declare both inputs as required, so a workflow run by a schedule trigger must remove event or make it optional; otherwise each firing records lastOutcome failed: Cannot start workflow "<name>": required input(s) not available: event, and a re-run returns HTTP 400 with the same message. See the Workflow Input Contract.

    The run's recorded inputs (the Inputs entry on the run's Overview tab) are the resolved standard inputs, without event; the event is shown as the run's trigger instead.

    Workflow runs have no outputs. The result of each step is available from the task output of the corresponding action node (and the submitted answers of each human-task node).

    Concurrency Rule

    A subject can have at most one active run per workflow definition (running or waiting status). Sequential runs of the same definition on a subject are fine once the previous run finishes, and runs of different definitions may be active on the same subject at the same time.

    A trigger that would violate the rule is handled as follows:

    Trigger Behavior
    Manual (Run workflow…, Re-run) Rejected with HTTP 409
    create-workflow routing rule Skipped (not queued); the skip is recorded in the routing outcome
    Schedule trigger Skipped (not queued); the trigger's last outcome is recorded as skipped

    Schedule Triggers

    A workflow definition can have zero or more schedule triggers, managed on the Triggers tab of the workflow definition page (REST: /api/v1/workflow/definitions/{workflowDefinitionId}/triggers/schedules). Each trigger has:

    Field Purpose
    Cron A 5-field Unix cron expression (minute hour day-of-month month day-of-week), evaluated in UTC
    Subject name Required; the fixed subject every run attaches to (at most 246 characters)
    Enabled Whether the trigger fires

    The subject is created on the first firing (with ref schedule:<subject name>) and reused on every later firing, so run history accumulates on one subject. Each trigger also reports:

    • Next run (nextRunAt) — when the trigger fires next; empty while disabled
    • Last run (lastRunAt) — when the trigger last fired
    • Last outcome (lastOutcome) — started, skipped (the subject already had an active run of the definition), or failed: <reason>

    Axiom checks for due triggers every axiom.workflow.schedule-poll-interval (default 30s). Firing assumes a single Axiom node; running multiple nodes against one database is not supported for schedule triggers.

    Re-running a Failed Run

    On a subject's Runs tab, each failed run has a Re-run button. After you confirm, Axiom starts a new run of the latest published version of the same workflow on the same subject. The new run keeps the original title and labels, and gets the extra label rerunOf:<original run id>. Its inputs are resolved again from the subject's current state; a run that was started from a stream event is re-run from that event, so the new run has the same context.event. The workflow's actions run again. Only failed runs can be re-run (REST: POST /api/v1/workflow/runs/{runId}/rerun; other statuses are rejected with HTTP 409).

    Dispatching Events to a Waiting Workflow

    Independent of create-workflow, a subscription routing rule of type workflow-dispatch broadcasts matching events to every workflow run currently parked at a receive-event node — regardless of which subscription originally started that run. Matching considers the parked node's declared event type and EL condition. When the event carries a recognizable ref, delivery is scoped to waiting runs on the correlated subject (all of them, across definitions); uncorrelated events are offered to every parked receive-event node of a matching type.

    A receive-event node can also declare:

    • correlationKey — {subscriptionKey, eventKey} EL expressions. The subscription key is evaluated against the run context when the node is reached and stored with the parked branch; only events whose evaluated event key is equal can match. match conditions still apply.
    • lookback — which already-stored events can satisfy the node when it is reached: run-start (default; events since the run started), none (only events that arrive later), or an ISO-8601 duration such as PT10M (never earlier than the run's start). Only events that matched the filter of a subscription with a workflow-dispatch rule are eligible, and an event never resumes the same run twice.
    • timeout — an ISO-8601 duration. If no matching event arrives in time, the run follows the node's timeout edge (isTimeout: true). Timeouts are checked every axiom.workflow.wait-poll-interval.

    A human-task node's optional title EL expression (e.g. 'Review ' += context.subject.ref) becomes the task's subject in the Inbox; it falls back to the node name.

    Following a Run

    Runs is Axiom's landing page (/runs). It lists every workflow run across all subjects with its status, title, subject, workflow and version, start time and duration. Filter chips narrow the list; see Runs. The same filters are available on GET /api/v1/workflow/runs as the status, definitionId, subjectId, and label query parameters (and triggerEventId for runs started from one event). Each run detail page has these tabs:

    • Diagram — the node graph with the run's progress; a node's menu opens its task's execution log
    • Overview — a form with the title (when the run has one), the subject and workflow (each linked to its page), the workflow version, status, start and end times, labels, inputs, the failure reason, a link to the trace, the triggering event (when started from an event), the events that resumed the run, and the tasks created by action or human-task nodes with their outputs and logs
    • Timeline — the nodes the run passed through, in order
    • Execution Trace — the run's trace, which records every node transition — see Tracing
    • Lineage — where the run came from and what it produced

    A run's status is running, waiting, completed, failed, or cancelled. The subject detail page's Runs tab lists every run (active and past) on that subject.

    A run parked at a human-task node surfaces its pending task in the Inbox; a run parked at a wait node resumes automatically once its resume time elapses; a run parked at a receive-event node resumes once a matching event is dispatched to it.

    Cancelling a Run

    Cancellation is per run: use Cancel run on the run detail page of a running or waiting run (REST: POST /api/v1/workflow/runs/{runId}/cancel). Cancelling marks the run cancelled, fails any in-progress task the run created, and removes any pending wait or event-subscription state associated with it. A cancelled run cannot be resumed. Other runs on the same subject are unaffected.

    Axiom SDK Functions

    The Axiom SDK is a set of functions for reading and updating Axiom data. They are available in two ways:

    • SDK action nodes — every SDK function appears in the workflow editor palette (as SDK: …, stored as sdk:<function>) and runs directly, without an AI agent
    • subjectId and runId default to the node's own run, so they can usually be left unmapped
    • the node's outputs join the run context without being declared: context.success, context.output (a message) and the function's result fields (for example context.title)
    • a failed call (for example an over-long title) fails the node, and so the run
    • Agent tools — an action type or session template can allow mcp__axiom-sdk__<function> in its Allowed Tools, making the function available to the agent through the axiom-sdk MCP server

    The authoritative list lives in core/src/main/resources/axiom-sdk-functions.json:

    Function Purpose
    axiom_list_subjects List subjects, filtered by name, labels, or ref; each result includes its derived active flag
    axiom_get_subject Get a subject (subjectId) including metadata, ref, and active
    axiom_create_subject Create a subject
    axiom_update_subject Update a subject's name, body, or labels
    axiom_update_subject_body Replace a subject's Markdown body
    axiom_add_subject_label / axiom_remove_subject_label Add or remove a subject label
    axiom_get_subject_thread Read a subject's thread
    axiom_add_thread_entry Post a message to a subject's thread
    axiom_list_events List events related to a subject
    axiom_get_task_status Get the status and details of a task on a subject
    axiom_respond_to_task Submit a response to a task awaiting human input
    axiom_get_workflow_run Get a workflow run (runId, required): title, status, subject, definition and version, labels, inputs, current node. In an sdk: action node, runId is filled in automatically with the node's own run.
    axiom_set_workflow_run_title Set a workflow run's title (runId, title; a blank title clears it; at most 500 characters). In an sdk: action node, runId is filled in automatically, so a node with actionType sdk:axiom_set_workflow_run_title and input title (for example 'Checking ' += context.subject.name) titles its own run.
    axiom_list_subject_runs List workflow runs for a subject (subjectId, required; optional status), newest first, at most 50
    axiom_fire_event Fire a new event into Axiom for processing by subscriptions and workflows
    axiom_get_activity_log Read the activity log, optionally filtered by subject
    axiom_list_tools / axiom_list_action_types / axiom_list_agents List configured tools, action types, and agents

    There are no SDK functions for creating tasks directly, closing or reopening subjects, or reports — work is started only by workflow runs, and subjects have no lifecycle of their own.

    Workflows in Configuration Packs

    Workflow definitions (including their published version history) are included in Configuration Packs export/import, and can be generated by the AI Assistant's Configuration Assistant. Workflows in an imported pack or applied by the assistant are validated and published; unchanged workflows are not re-published.

    Subscriptions that start workflows (create-workflow routing rules) may reference the workflow by name with workflowDefinitionName instead of workflowDefinitionId. Axiom resolves the name to the workflow's id when the subscription is created, updated, imported, or applied, which lets a pack or assistant session create a workflow and the subscription that starts it together.
